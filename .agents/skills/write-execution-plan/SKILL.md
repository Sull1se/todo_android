# 独立执行方案编写

## 触发与交付边界

**触发条件：** 维护者在当前任务或仍有效约束中明确交给其他 Agent 执行，且需要准备方案时使用。普通讨论、标准 Skill 直接执行、维护者要求当前 Agent 实施均不自动触发；只参考方案要素不等于调用交接流程。明确的执行指令及已授权的实施阶段优先，不因加载本 Skill 反复要求用户重新批准。单纯知识问答、进度查询、独立的文档体系维护不进入此流程。

**本次只生成方案，不执行方案中的变更。** 可以只读核查源码、配置和已有证据；只写方案文件及必要的索引、状态引用，并按仓库要求检查和提交这些文档。不得顺带修复业务代码、修改运行配置、构建安装、迁移数据或部署；将这些操作写成后续执行步骤。既有工作区变更不得覆盖或夹带提交。

先读 [项目入口](../../../AGENTS.md)、[总索引](../../../docs/index.md)、[当前问题](../../../docs/quality.md)、[文档规则](../../../docs/documentation.md) 及任务对应主文档。沿用已经完成的分析与证据，仅补齐交接必需的缺口。区分报告者反馈、代码可确认的事实、Agent 实测、推断和待验证假设，不能把推断写成确定根因。

## 保存与交接要求

- 在 `docs/` 下保存主题明确的独立 Markdown 文件，例如 `docs/<topic>-execution-plan.md`；不只在聊天输出，不创建长期计划目录。此类明确的方案交付是“一般任务不另建计划”的例外。
- 方案必须有文档规则要求的元数据、编写日期、生命周期和真实验证范围；新增后运行 `Sync`，在索引任务路由及相关未闭环问题处补充入口。
- 将方案作为独立交接件编写。接手 Agent 可从同一仓库读取源码和引用的主文档，但不能需要原对话、未附带的日志或另一轮设计讨论才能执行。核心结论、实施决策、验证标准和命令直接写入方案，引用只用于定位证据与规则。
- 方案使用仓库相对路径、文件名和函数/类/配置键定位代码；行号仅辅助定位。记录基线提交、相关未提交改动、应用/数据库版本及必要环境，不抄录密钥或密码。

## 方案必须包含的内容

### 1. 技术背景与执行基线

写明原始需求、可见现象、触发条件、影响范围、预期行为与不可破坏的约束。概括相关架构、数据流、状态归属、依赖版本和关键代码入口。对于已分析的问题，保存“现象 → 证据 → 机制 → 修复决策”的完整链路，注明证据日期/版本、已排除方向及尚不能确定的部分；新需求不强行虚构缺陷根因。

写明采用方案和取舍理由，不把多种待选路线留给执行者重新设计。若还存在影响正确性的未知项，给出精确检查方法、判定信号、各结果对应的执行分支与停止条件。确实无法决定时标为“阻塞、暂不可直接执行”，明确待补信息，不能用“自行排查”或假定事实掩盖缺口。

接手时只需核对基线和前置条件。若代码、版本或需求已经变化，先核对受影响的步骤；仅在证据失效时重新分析相关部分，不盲目重复旧方案或无条件重做完整分析。

### 2. 详细执行步骤

按依赖关系编号；每步写清输入/前置条件、目标文件与符号、具体修改内容、预期状态、检查点和失败处理。需要时提供算法、状态转换、接口/数据结构、事件时序、事务与持久化边界以及关键伪代码；仅写“优化性能”“修复状态同步”“补测试”不合格。

列明执行命令、工作目录、工具/环境前提、产物路径和必要的版本处理。给出适用的数据保留、备份恢复和回退步骤，说明回退适用版本与停止条件。既有授权及暂缓项需保留；需要另行获得授权的操作必须指明精确动作和时机，不代替用户扩大范围。

**无法回滚操作显式标记**：凡涉及无法回滚的操作（如破坏性清理未备份数据、设备端 `pm clear` 擦除用户生产数据、非兼容性数据库破坏性降级、覆盖或删除私钥凭据等），必须在步骤中显式标记为【无法回滚/高风险】，并注明在实际执行前必须获得更高层级的用户显式确认。

### 3. 本地验证措施

针对每项改动列出验证编号、前提、命令或操作、期望结果、失败判据、报告路径和覆盖限制。优先复用项目现有测试；新测试应验证行为或关键不变量。覆盖与本次问题有关的正常、边界、异常和回归场景，按风险选择编译、单元测试、静态检查或其他必要验证，不列无关全套测试。

**高保护级别规则**：关键测试、CI、Guardrail 校验脚本（如 `Manage-Docs.ps1`）与核心 Requirements 拥有比普通业务代码更高的保护级别。方案规划中严禁通过删除、注释或放宽测试用例与规则作为解决缺陷的手段，严禁通过降低既定需求让实现通过。

Android 构建与验证按 [开发与发布](../../../docs/development.md) 写入方案：明确构建变体、版本、单元测试与 lint 命令、复制至根 `dist/` 的命令与核验方法。Debug 构建不依赖发行私钥，是本地验证与执行 Agent 的默认路径；Release 交付依赖 `.signing/` 发行密钥与环境变量密码，仅由维护者执行，方案不得要求任何未授权人员或 Agent 获取凭据。此处的命令均是后续执行者要运行的步骤，不是规划阶段已经通过的证据。

### 4. 收尾验收措施：手动测试

提供维护者或报告者可以照做的测试矩阵：用例编号、验收对象/APK 版本、设备与数据准备、逐步操作、可观察的预期结果、通过/失败标准及需回报的信息。以可观察的行为表达标准，不用“确认实现正确”代替步骤。

明确 Agent 本地通过后交付产物，等待实际安装测试反馈；安装与手动场景由执行者完成。记录设备/系统、版本、逐项结果和异常复现信息；性能问题按需要记录发生阶段或视频等证据，不能凭感觉伪造帧率结论。构建通过、代码检查或 Agent 自测不能代替手动验收。

### 5. 验收后的项目文档更新与提交

将更新写成明确步骤并指定文件与章节。方案必须明确要求执行者在任务收尾时进行**知识影响判断**：
1. **Evidence 留存**：是否产生了需要长期保存的测试报告、验收反馈或关键决策证据；
2. **项目文档更新**：是否改变了应用逻辑、UI、数据模型、依赖、配置或已知问题；
3. **Skill 维护**：是否改变了工作流、角色边界或检查命令。
依据判断列出更新检查清单并执行。实现完成时先同步主文档、记录本地验证并保持“待验收”；反馈到达后，再记录绑定版本、日期、环境、方法、结果和未覆盖范围的验收证据。

按 [文档维护规则](../../../docs/documentation.md) 更新 [应用与架构](../../../docs/todo.md)、[开发与发布](../../../docs/development.md)、[当前问题](../../../docs/quality.md) 和 [验收与验证历史](../../../docs/verification-history.md) 中实际受影响的内容。满足关闭条件的完整问题记录连同解决版本/提交、关闭日期和证据立即迁至历史，同次提交从当前问题页移除；未通过、部分通过或证据不足的条目继续保留并写下一步。

更新方案生命周期：当前步骤已全部完成后按文档规则归档或标明已取代，保留设计与历史证据，修复索引和引用。写明收尾命令：`Sync`、`Check`、`git diff --check`、精确暂存、`Check -Staged`、Conventional Commit、提交后工作区复查；保留本次之外的改动。

## 规划阶段完成检查

以“只拿到方案文件和仓库的另一位 Agent”为视角逐项核对：是否仍要追问聊天背景、重新推导根因、选择未定方案、猜测命令/修改位置/验收标准。补足这些缺口后再交付；无法补足的明确标为阻塞。

执行文档检查，按项目约束提交方案与相关文档。在最终回复给出方案文件的本地链接、范围、阻塞项（如有）及验证边界，明确方案尚未执行；不把方案编写完成表述为功能修复完成。
