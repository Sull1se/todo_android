# Todo 文档维护规则

[文档总索引](index.md) · [当前问题与解决进度](quality.md) · [Agent 工作入口](../AGENTS.md)

## 文档责任与唯一落点

项目由维护者个人维护，不考虑社区共同维护；当前任务 Agent 参与提案、实现与文档同步。当前任务 Agent 必须维护相关文档，不等待另发更新请求。一般任务只需更新现有主文档及验证记录，不单建计划、复盘或审批文档。进入 `write-execution-plan` 流程时，必须在 `docs/` 保存独立交接方案；此例外不建立长期计划目录。日常任务收尾使用 `update-project-docs`；维护者独立要求全面维护文档时使用 `audit-project-docs`，不将每次普通任务收尾扩大为全量审计。标准路径存放的 Skill 自动注入 Agent 上下文；项目文档不得链接 Skill 文件。

## 规则冲突与事实优先级

先遵守运行环境、工具权限和安全限制。其后，当前任务中维护者明确作出的新决定优先于旧项目记录。

项目内按主题主文档决定现行规范；Plan、Skill、AGENTS.md、索引和摘要不得覆盖对应主文档。历史归档、旧 Plan 与旧 Evidence 只描述其记录时点，不作为当前规则。

源码、配置、测试和产物是现状或验证证据，不自动决定产品要求：源码与事实文档不一致时同步事实；源码与已确认需求不一致时登记 Quality Gap，不降低需求。

发现冲突时，先记录冲突位置、版本、范围和影响；仅暂停依赖该决定的操作。能由主文档或新决定解决的，更新所有派生入口并保留替代关系；两个同级主文档冲突或意图不清时，向维护者说明选项并等待决定。

## 高保护级别与安全操作治理

### 高保护级别规则

关键测试、CI、Guardrail（如 `Manage-Docs.ps1` 校验脚本）、核心 Requirements（业务需求、数据模型与迁移约束）和治理规则拥有比普通业务代码更高的保护级别：
1. **严禁弱化检查**：禁止 Agent 因检查或测试失败而直接删除、注释或放宽测试用例与校验规则，严禁通过降低需求或修改基线使有缺陷的实现通过。
2. **合规修正机制**：当规则或检查工具自身确实存在问题、过时或不兼容时可以修正，但必须在提交和交付说明中明确阐述修改原因、影响范围（Blast Radius）与验证方式，并严格遵循既有授权边界。
3. **免除额外审批**：日常的、已经获得授权的常规维护与合理演进，不额外引入不必要的繁琐审批流程。

### 不可逆操作显式标记

无法回滚的操作必须在执行前显式标记为【无法回滚/高风险】，并要求更高层级的用户显式确认：
- 破坏性数据操作：如无备份的数据库 drop、清空真实用户数据、非兼容性数据库破坏性降级等；
- 生产设备破坏性操作：如在测试设备上执行 `pm clear` 或 `adb uninstall` 导致应用本地数据擦除；
- 破坏性版本控制操作：如 `git reset --hard`、`git clean -fdx` 导致未提交工作或构建产物永久丢失；
- 敏感凭据操作：物理删除或覆盖签名证书、私钥文件等。

## 任务结束时的知识影响判断与收尾流程

所有任务结束前，必须严格执行**知识影响判断**三问：
1. **Evidence 留存判断**：任务是否产出了需要长期保存的证据？（如自动化测试执行结果、真机插桩通过报告、手动验收记录、APK 签名指纹/哈希、性能度量或重大安全决策）。若是，必须按 Evidence 规则将证据与版本/日期绑定，录入 [验收与验证历史](verification-history.md) 或相关主文档。
2. **项目文档影响判断**：任务是否改变了项目当前事实、设计或状态？（如应用业务行为、UI 与手势交互、排序逻辑、数据模型与迁移、构建依赖与 SDK、打包版本、已知问题等）。若是，对照职责表更新目标文档，并对设备序列号等敏感信息严格脱敏。
3. **Skill 维护判断**：任务是否发现现有 Agent 流程、角色职责边界、提示词指导或辅助脚本与实际脱节？若是，更新对应 `.agents/skills/<name>/SKILL.md`，同步元数据与描述。

> **重要原则**：这不是要求“每次任务都更新文档或 Skill”，而是要求“每次任务都判断是否需要更新”。纯查询或未改变状态的只读任务无需更新，在交付回复中说明依据即可；若判断需要更新，必须列出更新检查清单（Checklist）并逐项执行。

## 问题记录与关闭迁移

### 问题报告与记录要求

通过 Issue 报告问题或提供反馈时，报告者应提供以下信息，处理者按报告内容如实记录，不假设固定设备或版本，也不补造未提供的信息：

- **应用版本**：`versionName` / `versionCode`（应用内或关于信息），以及获取渠道（Release 下载或自行构建）；
- **系统环境**：Android 版本 / API 级别、设备类别（机型或形态）；
- **复现信息**：复现步骤、预期结果、实际结果、发生频率；性能问题记录发生阶段，必要时附视频；
- **脱敏要求**：日志、数据库备份与截图不得包含私人任务内容或凭据，提交前先脱敏。

维护者与 Agent 记录反馈时区分用户报告、代码可确认的事实、Agent 实测与源码推断，不假设任何固定设备或固定版本默认值。

### 问题记录与流转要求

**`quality.md` 的唯一作用是记录项目当前存在的问题及各自解决进度。** 只保留尚未闭环的 APP 应用问题和 DOC 文档问题，内容限于编号、优先级、状态、最近更新、问题及影响、证据摘要或链接、当前进度、阻碍、下一步和关闭条件。维护责任为处理对应任务的 Agent。代码已修复但未完成必要验收的条目仍属未闭环，不得提前移走。已关闭问题的列表、经过和历史摘要均不得在质量清单中保留或重新添加，统一在 `verification-history.md` 维护。

不在 quality.md 保存项目概览、最新版本表、历史验收、完整验证日志、已解决条目及其关闭摘要、通用回归矩阵或治理规则。项目概览归应用文档；源码配置与发布状态归开发文档；历史结果与已解决条目归 verification-history.md；维护机制归本文。没有未闭环问题时只写“当前无未闭环问题”，不保留已解决列表占位。

处理每个问题时必须遵循以下步骤：

1. **登记与推进**：复核是否已有相同编号，记录当前进度与关闭条件；暂缓和阻塞也继续保留。高优先级表示影响核心操作、数据或可信验收，中优先级表示行为/质量缺口，低优先级表示维护负担；历史编号不重用。
2. **记录证据**：每次实际验收或验证在 verification-history.md 记录日期、对象版本或提交、环境、方法、结果和未覆盖范围，区分用户报告、Agent 实测与源码推断。quality.md 仅更新当前进度和证据链接。
3. **关闭即迁移**：满足问题关闭条件后，在本次处理内立即将完整问题记录迁入 verification-history.md 的“已解决问题归档”，注明关闭日期、解决版本或提交、解决摘要、验证依据与保留的回归要求；同时从 quality.md 删除整条记录及专属详情，不在其中标“已解决”长期保留。迁移与验收记录在同一提交完成，不等待定期清理或下次任务。
4. **部分完成**：仅关闭实际满足条件的条目；未通过或缺少必要证据的条目继续在 quality.md 记录具体阻碍，不能通过降低关闭条件完成迁移。
5. **回归与收尾**：原问题重新出现时，将原编号重新登记到 quality.md，并链接历史关闭记录；新问题使用新编号。同步主文档、方案中的现行摘要和链接，运行 Sync、Check、暂存检查及差异检查后提交。

提交前 Agent 必须逐项确认：quality.md 仅含未闭环问题，所有移出问题都有历史去向，迁移没有丢失证据，新文档已被索引且实际暂存。当前工具检查目录、元数据、索引、链接、可达性与生成配置；**问题是否已解决、是否应迁出属于 Agent 的语义核查，脚本不会自动判断或搬移。**

## 每次任务的维护循环

1. **开始：** 读入口、索引、状态页，查工作区和近期相关代码变化，运行 `Check`。检查本地钩子配置，已有其它钩子时先了解并保留其用途。
2. **知识影响判断：** 任务结束时执行 Evidence、项目文档与 Skill 三问评估，列出检查清单。
3. **变更与纠偏：** 按上表定位文档，搜索旧路径、名称、版本和行为；同步正文、关联实现及索引。直接修正证实过时的描述，删除失效步骤，保留必要决策背景。代码违背需求、证据不足或超出范围时，记到状态页并给出下一步，不把缺陷包装为新需求。
4. **生成：** 执行 `Sync`；新增/移动/删除文档自动重建总索引与归档索引，配置变化重建配置表。工具不自动改业务正文、验证结论或日期。
5. **验收与提交：** 执行 `Check`、适用行为验证和差异检查；将验证结果写入验收与验证历史，按上节立即迁出已解决问题；清理临时文件，暂存后执行 `Check -Staged` 并提交。

依赖升级、迁移、发布准备或文档冲突时，额外检查相关主文档的整个流程和状态页缺口。平时随任务小步巡检，没有常驻进程、定时后台任务或多人审批。

## 正式文档与元数据

正式知识文档为根 `AGENTS.md` 与 `docs/` 下的 `.md` 文件；项目 Skill 入口 `.agents/skills/<name>/SKILL.md` 是受管流程文件，仍检查元数据、正文链接和误忽略情况，但不进入文档总索引，也不要求从文档入口可达。标准路径 Skill 由环境自动注入 Agent 上下文，任何受管 Markdown 文件都不链接 Skill。总索引登记根入口与 `docs/` 下除具体归档页以外的正式文档；归档索引集中登记归档页，不预建多层空索引。使用 UTF-8、一个一级标题；普通文档使用以下平面文本头部，值必须填实，不提交占位符：

```yaml
---
title: 清晰主题名称
purpose: 本文回答什么问题
status: 当前有效
owner: 当前任务 Agent；维护者负责审阅与合并
scope: 对应模块或流程
updated: 2026-10-02
verification: 未验证
verified: 尚未执行验证；列明下一步
---
```

- `status` 为草案、当前有效、已取代或历史归档；已取代页须链接当前主文档并说明原因。
- **README 治理豁免：** 根 `README.md` 是面向访问者的产品入口页，按维护者决定**不纳入**本检查器的元数据、链接、索引与可达性检查，检查器在其上不做任何格式要求；其内容质量由维护者人工把关。正式知识文档仍为根 `AGENTS.md` 与 `docs/` 下的 `.md` 文件。标准 `LICENSE` 是许可证原文，不插入项目 YAML 元数据，不作为受管 Markdown 检查。
- **历史归档必须归位与收口**：凡元数据 `status: 历史归档` 的文档，必须存放在 `docs/archive/` 下；标记归档时须在同次变更中迁入，已有未归位文档也须迁移。总索引不链接具体归档文档，而是通过归档索引（`docs/archive/index.md`，存在归档文档时由 `Sync` 生成，不预建空索引）集中链接与呈现。迁移保留文件名、历史正文和证据，修正页内相对链接、全部入链与过时的路径说明，执行 `Sync`、`Check` 和暂存检查后提交。持续维护且标记为“当前有效”的验收历史等文档不因包含历史内容而迁移。
- `verification` 为未验证、已静态检查或已在指定环境验证；`verified` 写真实日期、环境、方法、边界，详细结果统一存放验收与验证历史。生命周期与验证状态独立。
- `updated` 是实质维护日期，不代替验证日期；生成内容不嵌运行时间，重复执行应无差异。
- 使用相对内联 Markdown 链接，锚点对应实际标题，不使用个人绝对路径或 `file://`。参考式链接与 HTML 链接不在当前支持范围，须改为内联形式。
- 新页补齐元数据后执行 `Sync` 自动登记；高频主题另在索引的任务路由补入口。移动/删除后须修复其它引用，不能只重建登记表。
- 项目 Skill 使用标准顶层 `name`、`description`，随后在 `metadata:` 下以两个空格缩进存放上例八个治理字段；值为单行纯文本，不使用折叠、多行或其它嵌套。`name` 与目录名一致，使用小写字母、数字及单连字符，最长 64 字符；`description` 为 1–1024 字符，不含尖括号，明确触发边界。检查器读取治理字段并校验 Skill 正文中的链接；不生成总索引条目，也不要求 Skill 从文档入口可达。项目文档链接 Skill 时检查失败。不把项目治理字段放到 Skill 顶层。此规范只适用于本仓库，不声称覆盖完整 Skill YAML 语法。
- 正式范围及上述 Skill 入口之外的 Markdown、MDX、RST、TXT 等说明会报错要求整理（根 `README.md` 为唯一显式豁免，见上）。Skill 后续如需辅助知识页，先纳入受管目录和检查规则，不能以整个 `.agents/` 排除检查。生成日志和缓存不进入知识库；长期保留的结果必须由主题文档链接并解释用途、来源和验证范围。
- 工具盘点 Git 跟踪文件与未忽略的新文件，并额外检查 `docs/` 与 `.agents/skills/` 中被误忽略的文档。临时输入可由明确的本地 Git 排除规则管理，不得隐藏正式文档。

## 工具与操作

只依赖 Git 和 PowerShell 7。在根目录执行：

```powershell
pwsh -NoProfile -File scripts/docs/Manage-Docs.ps1 -Mode Sync
pwsh -NoProfile -File scripts/docs/Manage-Docs.ps1 -Mode Check
pwsh -NoProfile -File scripts/docs/Test-Docs.ps1
git diff --check
```

- `Sync` 只更新总索引的 `docs:index` 区域、归档索引的 `docs:archive` 区域与开发文档的 `docs:config` 区域；输入是文档头部和代码配置，不手改生成区。
- `Check` 只读校验工作区；失败输出规则、位置、修复提示并返回非零；成功报告文档数、本地链接数、生成块数和检查范围。
- `Check -Staged` 从 Git 暂存区读取文件、链接目标与配置，防止工作区正确而实际提交遗漏。
- `Test-Docs.ps1` 在 `scripts/docs/.test-work/` 建隔离仓库，验证正常及故障场景，结束自动清理。它是工具回归检查，不是 Android 测试；只改正文不必每次重跑整套工具测试。

## 本地提交检查

新克隆不继承 Git 本地配置；首次任务先执行：

```powershell
git config --get core.hooksPath
```

若为空，或确认没有需要保留的自定义钩子，启用仓库内钩子：

```powershell
git config --local core.hooksPath .githooks
```

仅影响当前仓库。钩子在提交前调用 [Check-Local.ps1](../scripts/quality/Check-Local.ps1) `-Mode Commit`，自动对暂存区运行受管文档检查与格式检查；对代码变更自动触发单元测试与 `lintDebug`。失败后先修正问题、运行 `Sync`、复查并重新暂存，再提交。钩子不自动暂存，严禁使用 `--no-verify` 跳过钩子交付。

Git 允许人为绕过钩子，配置也不随克隆传播，因此入口同时要求每次任务主动检查。GitHub CI 工作流（`.github/workflows/ci.yml`）在远程复用相同检查；本地成功不等于远程运行成功，远程结论以实际运行为准。

## 检查范围

| 规则 | 失败条件 | 修复 |
| --- | --- | --- |
| DOC-SCOPE | 正式范围之外的文档、被误忽略的受管文档或未支持格式 | 移入正式目录并转换格式；生成物明确归属与排除 |
| DOC-META | 字段缺失、状态非法、日期无效或一级标题数量不对 | 补真实元数据，不伪造验证 |
| DOC-GENERATED | 索引/配置表与输入不一致，或标记损坏 | 核对输入后 `Sync` 并审阅差异 |
| DOC-LINK | 目标/标题不存在、路径越界、语法不支持，或受管 Markdown 链接 Skill | 改成有效的相对内联链接；删除指向 Skill 的链接 |
| DOC-REACHABLE | 根入口和 `docs/` 受管文档不能从根入口沿链接到达 | 修复入口或索引链；Skill 由标准路径自动注入，不检查文档可达性 |
| DOC-SOURCE | 生成所需配置缺失或无法唯一解析 | 对照代码调整生成器，不保留旧表蒙混通过 |

检查可发现孤立页、断链、登记遗漏和生成表覆盖的配置漂移，不能判断所有业务语义、外部链接、签名兼容性或真机结果。Agent 仍需对照实现及证据核验，不能只因结构通过就关闭应用缺口。

## 维护机制与部署状态

采用少量主文档和本地工具：生成器维护索引与配置值，Agent 维护语义和证据。一般任务不建独立计划，历史由 Git 追溯。GitHub CI 复用本地检查命令；在 CI 实际部署并运行成功前，不把本地通过说成远程通过。
